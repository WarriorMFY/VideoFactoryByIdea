# 小循环 9 · 49 分钟长视频压测 + 术语一致性审计

> 一句话：49 分钟的片子**能跑通、能出片**（48.7 分钟成片 / 273 条字幕 / 校对表 273 行），
> 成本主要在**两次渲染（约 22 分钟）+ 识别（约 6.5 分钟）**；长片规模下暴露并修掉了 2 个短片永远踩不到的 bug。

## 1. 为什么做这一轮

前面 8 轮的素材都是 30–90 秒。真实交付是 20–60 分钟。规模问题（耗时、字幕条数、校对表行数、机翻脏数据）
在短片上一辈子都暴露不出来。这一轮把 **49 分钟** 跑通，并顺手补上"术语一致性审计"。

**素材诚实说明**：合法长片只有 Tears of Steel（12 分钟，CC-BY），用 `-stream_loop` 拼成 49 分钟。
**测的是规模与稳定性，不是内容多样性** —— 所以这轮的成片不能用来评判"剪得好不好"。

## 3. 长片才暴露的两个 bug（都已修）

1. **回写会 trim 译文** → 279 行里 6 行带前导空格的译文（`" Id"` / `" Sorry."`）对不上，"恒等回写"失效。
   修法：`apply_review` 只判"是否空白"，原样写回。
2. **机翻返回脏数据** → MyMemory 偶发给出 `<strong>%2$s</str…`、`%2$s` 占位符、带前导空格的片段（279 行踩到 6 行）。
   修法：`make_subs` 增加 `cleanMt()`（去标签/解实体/删占位符/折叠空白），模板残留视为失败重试。
   修完复查：273 行里 `<>`/占位符/多余空白 **0 行**、空译文 **0 行**。

## 4. 新增能力：术语一致性审计

`export_review` 会用术语表反查两类问题（写进 `review.csv` 的 flags 与 `review.json` 的 `term_audit`）：

- `term_missing`：英文里出现了规范术语（`LUFS`/`Mbps`），中文里找不到它 —— **最常见的原因就是被行宽切行切断**；
- `term_variant`：译成了术语表里记录的错法（如「卢夫斯」）。

回归用例就是小循环 8 里人工修掉的那个毛病（`−16 LUFS` 被切成 `…−16 LU` + `FS，…`），审计能自己指出来。

## 6. 限制

- 渲染降到 640×360（压测省时间）：编码器/滤镜链/字幕烧入路径与 720p 完全一致，只是像素少；
- 素材是循环拼接，剪辑规则会看到重复的"黑场/冻帧"，不能用来评判剪辑决策；
- 术语审计只认术语表里的规范写法，`megabits per second` 这类复数变形暂不匹配（已知，待补）；
- 逐词高亮（karaoke）在 49 分钟上的**事件数**这一轮没单独测（`make_ass` 只在 90s 样本上验过像素级正确性）。
  按 90s→约 20 词/句、273 条字幕估算，49 分钟约 1–1.3 万条 ASS 事件（与小循环 5 的估计一致），待下一轮实测。
