## 为什么这一轮值得做

上一轮的校验器只看 `Prototype/` 与 `log.md` 的三件套，§3.3 这条**作用于全仓的规则**从来没有被检查过。第一次真正去量，量出的是规则自身的漏洞：

| 层 | 目录数 | 本轮前已有同名索引 | 按字面执行要造 |
|---|---|---|---|
| `History/` | 225 | 0 | ~130 |
| `Prototype/` | 159 | 38 | 16（真实欠账） |
| `Tool/` | 9 | 9 | 0 ✅ |
| `Skills/` | 9 | 9（SKILL.md） | 0 ✅ |
| `Material/` | 9 | 0 | 1 |

`History/publish/bilibili/runs/` 下 88 个时间戳目录、`History/runs/` 下 24 个一次性 run——它们是**机器留下的产物**，不是给人逐层下钻的导航单元。给它们各造一个索引，既没人会读，也让同节「不批量造空壳」那句话失效。

**规则缺的不是执行，是适用范围。**

## 零内容丢失核验

对每个被删除的 md，取 `HEAD` 版本的全部非空行（≥6 字符），逐行在新索引里查找（去标题符号与空白后比对）：

```
合计 47 个被合并文件，缺失 0 行
46 个 Prototype 文件命中率 1.000；ARCHIVE.md → SKILL.md 同样 0 缺失
```

这不是"看起来都在"，是可重跑的核验——脚本落在 `Workspace/tmp/verify_merge.mjs`（一次性，未升格工具）。

## 结论

- **规则的适用范围比规则本身更重要**：同一条「每目录一个索引」，全仓执行会造 130 份空壳，限定了范围之后只剩 16 处真欠账。
- **机械执行必须先有工具**：合并 46 个文件靠脚本，但"没丢内容"必须靠逐行核验，靠眼睛看三份就是自欺。
- **结构变更必然产生引用欠账**：一次合并引出 12 处路径更新，不 grep 一遍就会留下断链——这一步不能省。
