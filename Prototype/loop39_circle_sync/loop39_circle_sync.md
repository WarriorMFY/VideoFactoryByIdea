## 结论

**开工落款，收工补全，反馈回填。** 三个写入时机全部绑在人工闸门上，不绑在"想起来了"上——因为 loop32–38 整整七轮零条目，证明"结轮时一次性写"这个隐性约定靠不住。

## 三段式写入

| 时机 | 写什么 | 为什么是这一刻 |
|---|---|---|
| 闸门一放行 | 锚点 + 标题 + 开始时间 + 初始目标 + 「结束结果：进行中」 | 存在性先落定。中断也只是一条"未完成"，不是整轮蒸发 |
| 闸门二提报 | 补：动作、结束结果、产物 | 三项结轮才确定；提交前写，与 git 时间戳对齐 |
| 人反馈到达 | 回填人工反馈 | 反馈在下一轮开头才到；不等它，这栏永远是空的 |

过程中的每个动作**不写进日志**——那属 `History\runs\`，日志只留一轮一条摘要。

## 双链：同刻创建

闸门一放行时三件事一次做完，缺一即为欠账：

1. 建 `Prototype\loopNN_<短名>\` + 同名索引 `loopNN_<短名>.md`（§3.3）；
2. `log.md` 落款，「产物」栏首项指向该索引；
3. `Prototype.md` 增量清单加一行，日志列指向 `log.md#loopNN`。

索引顶部回链日志锚点，条目指向索引——两侧互为锚点，任一侧改名，另一侧断链一眼可见。锚点与链接必须同一次提交落地。

## 未完成条目的样子

结轮中允许缺行，只有三行即可：

```
| 开始时间 | 2026-11-07 10:35 |
| 初始目标 | …… |
| 结束结果 | **进行中**（未收工；收工时补动作/产物/人工反馈） |
```

**不再填「待回填」**——历史上大半个库都是这个占位符，没人回来填过，等于失效标记。

| 码 | 含义 |

| W2 | 索引缺回链日志锚点 |
| **W3** | git 最后实质改动晚于日志最后条目——可能有工作没写进日志 |

### 第一版的漏洞（10:57 修正）

初版把"清单里日志列写着「缺」"当成提示信息打印，**不计入错误、退出码仍为 0**。也就是说 loop32–38 那种病，工具算得出数据却不判它错；更糟的是，"缺"字本身靠人记得在清单里写——漏写日志的发现，仍绕回了记忆。

补了 **E5** 后，`loop32–38` 七条被精确点名，退出码转为 1。同时补 **W3** 覆盖"连目录都没建的纯维护轮次"（脚本看不见痕迹，只能比对 git 与日志的时间线）。

W3 自身也修了一处静默失效：日期原取全文最大匹配，而日志正文里有 `validUntil 2026-11-14` 这类未来日期，会让 `gitDate > logDate` 永远为假、W3 永不触发。现改为只读条目日期字段（`| 开始时间 |` 或标题日期），并把两个日期输出到 `--json` 的 `timeline`，让"没触发"可被看见。
